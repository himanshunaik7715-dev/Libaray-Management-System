# Project Rules

## Scope rules (must follow)
1. Implement **only** book catalog, member registration, issuing, returning, overdue fine and book search/filter.
2. Use React + Vite for UI and **Core Java built-in HTTP server** for backend; **do not** add Spring Boot, Express, ORM, database or third-party Java dependencies.
3. Store `Book`, `Member` and `IssueRecord` in Java `ArrayList`s; use linear loops to demonstrate DSA.
4. Keep a single-page UI with Books, Members and Issue / Return tabs.
5. Do not introduce authentication, administration, dashboards, notifications, renewals, reservations or payment processing.
6. Favor small readable code and completing a working demo over architecture abstractions.

## Library rules
- Book and member IDs must be positive integer IDs generated by the backend.
- A book is a single loanable copy. Only available books may be issued.
- An issue references an existing book and existing member.
- Set `issueDate = LocalDate.now()` and `dueDate = issueDate.plusDays(7)`.
- Return only a currently issued book; calculate and present late days and fine.
- `lateDays = max(0, DAYS.between(dueDate, LocalDate.now()))`; `fineINR = 5 * lateDays`.
- Restoring book availability happens when its active issue record is marked returned.
- Reject missing required names/titles and nonexistent/invalid IDs with descriptive errors.
- Search is case-insensitive and matches title or author; availability filter supports all/available.

## Engineering rules
- The Java API returns JSON; POST input uses URL-encoded form data.
- React renders API result/error messages; never silently ignore API failures.
- Keep API paths fixed: `/books`, `/members`, `/issue`, `/return`.
- React calls relative `/api/*` endpoints. Root `vite.config.js` proxies and rewrites `/api/*` to Java `http://localhost:8080/*`; Java routes retain `/books`, `/members`, `/issue`, `/return`.
- No database or persistent files; warn that restart resets state.
- Use basic semantic HTML, labels, keyboard-accessible forms, visible focus and adequate contrast.
- Match the **adapted** design in `DESIGN.md`, sourced from `IP-DESIGN.md`. Functional accuracy takes priority over animation.
- Do not add libraries just to implement simple visual styling.

## Change control
Before proposing a change, answer: (1) Is it explicitly in the problem statement? (2) Is it needed to make one of the six features work? If both are no, defer it. Keep `PRD.md`, `TASKS.md`, and `MEMORY.md` aligned with material changes.

## Minimum quality gate
- Java compilation succeeds.
- Frontend opens and reaches backend.
- Add/list/search/filter work.
- Register/list members work.
- Issue and return update book status; returned book can be reissued.
- Invalid IDs, duplicate issuing and invalid returning report errors.
- A fine never becomes negative; due-date calculation is correct.

## Approved source layout
- All source files live directly in the project root: `LibraryServer.java`, `App.jsx`, `App.css`, `main.jsx`, `index.html`, `vite.config.js`, `package.json`. No `frontend/` or `backend/` source folders.
- Run Java and Vite in separate terminals from the same root folder.
- The source-code migration is pending; do not claim it has already happened.

## Architecture change approval gate
- Treat `ARCHITECHTURE.md` as **frozen**. Do not edit, replace, or restructure its content without the user's explicit approval of a specific proposed change.
- If a change seems necessary, explain what would change and why, then wait for approval before updating the architecture document or implementing the change.
- Updating task checklists or design documentation does **not** imply permission to change the architecture.
